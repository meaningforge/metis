# RFC-0035: Concrete SQL Dialect Rendering

> **Design history:** This RFC preserves its original lifecycle status and rationale.
> Implementation claims describe the recorded design, not a guarantee that every
> proposed API remains current. See [current documentation](../../README.md) for
> supported interfaces. Package paths have been updated for this repository.

- **Status:** Implemented
- **Owners:** Metis maintainers
- **Created:** 2026-08-21
- **Last updated:** 2026-08-22
- **Scope:** `compiler.CompileTarget`, `sql`, `sql/render`, native-engine capabilities, expression target resolution, real-engine conformance, target evidence, examples and release documentation
- **Supersedes:** None

## Summary

Metis should expose only **concrete execution dialects** as SQL compile targets.

The current `ansi` target mixes two different concerns:

1. SQL rendering behavior that several concrete renderers may happen to share; and
2. a public physical target that callers can select and that conformance evidence presents as if it were an executable dialect.

RFC-0035 separates those concerns.

The public native-engine dialect set becomes:

```text
clickhouse
doris
duckdb
```

`duckdb` becomes a first-class renderer and compile target, at the same level as
`clickhouse` and `doris`. The public `ansi` dialect is removed.

Shared SQL rendering rules may exist as unexported implementation infrastructure,
but Metis should stop naming that infrastructure `ANSI`. Use neutral names such as
`default`, `common`, or narrowly named rendering helpers. No public
`CommonDialect`, `PortableDialect`, or replacement pseudo-dialect is introduced.

This RFC is intentionally about the **physical SQL renderer boundary**. It does
not rename or remove Ossie-defined `ANSI_SQL` expression fallbacks, because those
belong to the semantic-model contract rather than Metis's physical target registry.

## Decision

Five rules are normative.

1. **A public SQL dialect MUST identify a concrete execution target whose syntax
   and semantics Metis is prepared to generate and validate.**
2. **`ansi` MUST NOT remain a public `CompileTarget.Dialect`, native-engine
   capability, renderer registration, conformance target, or evidence row.**
3. **DuckDB MUST be represented explicitly as `duckdb`, with its own renderer,
   tests, target registration, and real-engine evidence.**
4. **Shared/default rendering behavior is implementation infrastructure, not a
   target identity. It MUST remain internal and MUST NOT be presented as an ANSI
   standards-compliance claim.**
5. **Where supported engines are known to disagree, the shared rendering layer
   MUST NOT provide a default answer. Each concrete dialect MUST make the choice
   explicitly; a missing override is a correctness gap and MUST fail closed.**

The resulting model is:

```text
                           SemanticPlan
                               |
                               v
                            SQL AST
                               |
               +---------------+---------------+
               |               |               |
               v               v               v
          DuckDBDialect   DorisDialect   ClickHouseDialect
               |               |               |
               v               v               v
            DuckDB           Doris          ClickHouse

         internal shared/default rendering helpers
               ^               ^               ^
               +---------------+---------------+
          implementation reuse only; not a public dialect
```

## Motivation

### `ansi` currently claims more than Metis has proved

Today the default registry contains:

```go
render.ANSIDialect{}
render.DorisDialect{}
render.ClickHouseDialect{}
```

and `ANSIDialect.Name()` returns `"ansi"`.

That makes `ansi` observable through native-engine capabilities and selectable via
`CompileTarget.Dialect`. The compiler then returns a physical SQL query whose
`Dialect` is also `ansi`.

The executable evidence added in #385 is valuable, but its actual proof is:

> SQL generated by the current `ansi` renderer executes correctly on DuckDB for
> the required Metis conformance corpus.

It does **not** prove that the same output is portable across PostgreSQL, SQLite,
Trino, or an unspecified family of ANSI-compatible engines. The distinction is
not theoretical: executing the corpus on DuckDB already exposed result-type
behavior around `DATE_TRUNC` and date-plus-interval expressions that differed from
Doris and ClickHouse.

A single concrete engine passing a corpus is strong evidence for that engine. It
is not evidence for an abstract standards target.

### A physical compile target should answer "where will this SQL run?"

Metis already models semantic engine selection and SQL dialect selection as
separate concerns. At the physical SQL boundary, the useful caller contract is:

```text
engine = metis-native
dialect = duckdb
```

not:

```text
engine = metis-native
dialect = ansi
execution engine happens to be DuckDB
```

The latter requires a hidden mapping from an abstract dialect to an actual engine
and weakens capability negotiation. If an Agent or execution binding knows the
database is DuckDB, the compile target should say DuckDB.

This becomes more important as target-specific differences grow. A concrete target
can own explicit behavior for time arithmetic, quoting, type coercion, percentile
functions, semi-structured values, null ordering, and future engine extensions.
An abstract `ansi` target has no authoritative engine whose behavior resolves those
questions.

### `ANSI` is also the wrong name for internal reuse

A renderer can use broadly standard SQL syntax without implementing the ANSI SQL
standard as a product contract. Naming shared helpers `ANSI` creates an avoidable
standards-compliance implication and encourages future code to ask "is this ANSI?"
rather than "which concrete target owns this behavior?"

RFC-0035 therefore does not replace `ansi` with another public portability label.
The shared implementation layer should use neutral names such as `default` or
`common`, or better, narrowly named helpers for the behavior actually shared.

### The current code does not have a shared default renderer to move

The current implementation is more duplicated than the phrase "move the default
renderer" suggests. `sql/render/ansi.go`, `sql/render/doris.go`, and
`sql/render/clickhouse.go` are three independent implementations. Doris and
ClickHouse do not delegate to the ANSI renderer.

A review of the current files found substantial structural duplication:

| Renderer | Lines | Structurally identical to `ansi.go` |
| --- | ---: | ---: |
| Doris | 364 | 225 (62%) |
| ClickHouse | 422 | 235 (56%) |

One representative predicate-rendering path is effectively duplicated across all
three; the ANSI-to-Doris difference in that block is only a local variable name.
The important conclusion is not the exact percentage. It is that Metis currently
has **three renderer forks containing roughly 460 duplicated lines of rendering
logic**.

That is correctness debt. A rule fixed in one fork and missed in another may look
like an intentional dialect difference because each renderer is tested against its
own output. Extracting a shared baseline is therefore also an audit of whether the
three forks have silently diverged.

The migration is correspondingly non-trivial: at review time, **36 repository
files reference `ansi`** across Go, YAML, JSON, shell, and Markdown. RFC-0035 must
not describe the change as a simple symbol rename.

## MetricFlow prior art

MetricFlow provides a useful separation of these concepts.

Its `DefaultSqlPlanRenderer` is documented as rendering a SQL plan following ANSI
SQL, so broadly portable/default syntax exists as an **implementation baseline**.
However, MetricFlow does not expose an `SqlEngine.ANSI`. Its engine enumeration is
concrete and includes values such as DuckDB, Postgres, Snowflake, BigQuery, Trino,
and others.

MetricFlow also has a concrete `DuckDbSqlPlanRenderer` that builds on the default
renderer and overrides DuckDB-specific behavior.

Relevant upstream files:

- `metricflow/sql/render/sql_plan_renderer.py` — `DefaultSqlPlanRenderer`
- `metricflow/protocols/sql_client.py` — concrete `SqlEngine` enumeration
- `metricflow/sql/render/duckdb_renderer.py` — `DuckDbSqlPlanRenderer`

Metis should adopt the same architectural principle, not necessarily the same
inheritance mechanism. Go composition and unexported shared functions are a better
fit than Python subclassing.

The principle is:

```text
default/common SQL rendering behavior = implementation reuse
concrete database dialect              = public compile target
```

There is one additional Metis-specific constraint: shared behavior is allowed only
where it is actually shared. Known semantic divergence is not a place for a
convenient default.

## Proposed design

### Public dialect inventory

After implementation, the default native dialect registry MUST expose exactly the
concrete renderers that Metis currently supports:

```text
clickhouse
doris
duckdb
```

Alphabetical ordering is an implementation detail of `DialectRegistry.Names()`;
the important contract is that `ansi` is absent and `duckdb` is present.

A representative registry shape is:

```go
func DefaultDialectRegistry() *DialectRegistry {
    return NewDialectRegistry(
        render.DuckDBDialect{},
        render.DorisDialect{},
        render.ClickHouseDialect{},
    )
}
```

`DuckDBDialect.Name()` returns `"duckdb"`.

### DuckDB owns its physical SQL contract

The current DuckDB execution corpus is no longer described as an engine used to
validate some separate `ansi` target. DuckDB becomes both:

- the named physical dialect Metis emits; and
- the engine used to execute and validate that dialect.

The contract becomes direct:

```text
CompileTarget.Dialect = "duckdb"
          |
          v
     DuckDBDialect
          |
          v
      DuckDB SQL
          |
          v
      DuckDB CLI
```

This does not require Metis to own query execution in production. Real-engine
conformance remains test infrastructure. It simply aligns the renderer identity
with the execution semantics the renderer is claiming.

### Remove the public `ansi` renderer rather than alias it

RFC-0035 recommends a clean cut, not a permanent compatibility alias:

```text
ansi -> duckdb
```

must **not** become an implicit runtime mapping.

An alias would preserve the same conceptual ambiguity: callers could continue to
request `ansi` while receiving DuckDB semantics. It would also make target
capabilities and evidence harder to interpret.

Because Metis has not yet published a v0.1.0 release tag or a documented external
production compatibility commitment, this is the cheapest point to correct the
contract before it becomes durable.

A remaining request for `ansi` should fail through the normal unsupported-dialect
path rather than silently changing meaning.

### Internal common rendering baseline

There is no existing default renderer to relocate. Implementation Step 1 must
**extract** common behavior from the three independent renderer forks.

The implementation SHOULD preserve reuse where it is real, but MUST stop exposing
that reuse as a dialect. Acceptable shapes include:

```text
sql/render/default.go
sql/render/common.go
```

with unexported helpers, or smaller behavior-specific shared files for identifier
quoting, predicates, ordering, select mechanics, and other genuinely common rules.

The implementation should prefer the smallest useful abstraction. RFC-0035 does
not require a monolithic `DefaultRenderer` type if plain Go functions compose more
cleanly.

Physical-renderer symbols and filenames introduced or retained by this migration
SHOULD avoid `ANSI` terminology unless they specifically refer to an external SQL
standard or an upstream Ossie field.

Examples of names to retire from the physical renderer layer include:

```text
ANSIDialect
ANSIDialectName
renderANSISelect
renderANSIExpr
quoteANSIIdentifier
sql/render/ansi.go
```

The exact replacement names are implementation details, but they must not recreate
an abstract public dialect under another label.

### Common mechanics may be shared; known semantic choices may not

A concrete renderer may delegate genuinely identical mechanics to shared helpers.
For example, select-list layout or a predicate form that is proven identical can
be factored once.

However, **known dialect divergence creates a mandatory override boundary**.
Where supported engines differ in syntax, type behavior, null behavior, function
semantics, or other observable results, the common layer MUST have no usable
default for that choice.

Conceptually:

```text
known identical behavior
        |
        v
shared helper is allowed

known divergent behavior
        |
        v
shared layer: no answer
        |
        +--> DuckDBDialect MUST decide
        +--> DorisDialect MUST decide
        `--> ClickHouseDialect MUST decide
```

A missing concrete implementation must fail closed during compilation or an
equivalent pre-render validation step. It must not silently inherit plausible SQL.

`DATE_TRUNC` return typing is the worked example. DuckDB follows timestamp-return
semantics in cases where Doris and ClickHouse return a date. #385 exposed exactly
this bug class. There is no correct cross-engine default for the physical choice,
so a future Postgres or Snowflake renderer must not obtain one merely by failing to
write an override.

This follows the same Metis principle used for unknown functions, unregistered
error codes, unsupported semantic-critical extensions, and unproven aggregation
rollups: **absence of proof is not permission to guess**.

## Expression fallback is a separate axis

Metis must not confuse the physical-dialect change with Ossie's expression
selection vocabulary.

An Ossie semantic expression may provide target-specific forms plus an `ANSI_SQL`
fallback. That fallback means "use the model's portable SQL expression when no
more specific expression is available". It does not imply that Metis has a
physical `ansi` renderer.

The target-resolution model remains conceptually:

```text
CompileTarget.Dialect = duckdb
          |
          v
look for DuckDB-specific model expression
          |
          +-- found --> use it
          |
          `-- absent --> consider upstream ANSI_SQL fallback
                           if the resolver proves it is valid for this target
```

The physical renderer still remains DuckDB. A query using an `ANSI_SQL` model
expression therefore returns:

```json
{"dialect":"duckdb"}
```

not `ansi`.

This separation is important for future Postgres, Snowflake, and other targets:
one portable model expression may be reusable across several concrete renderers
without turning `ANSI_SQL` into an execution engine.

## Conformance and evidence

### Evidence tables name what was actually proved

After migration the target evidence should read:

| Target | Compiler conformance | Real-engine result conformance |
| --- | --- | --- |
| DuckDB | required corpus | DuckDB execution evidence |
| ClickHouse | required corpus | ClickHouse execution evidence |
| Doris | required corpus | Doris execution evidence |

There is no ANSI row.

Every row then answers the same question:

> Does Metis generate SQL for this named target, and does that target execute the
> required corpus with the expected results?

### The migration itself has a byte-identity contract

RFC-0035 separates **identity/refactoring changes** from **semantic SQL changes**.
That separation is mandatory for reviewability.

The existing Ossie conformance tooling already emits a per-case SHA-256
fingerprint. Before implementation Step 1 begins, the current fingerprints for all
96 canonical scenarios MUST be captured for each existing renderer. Step 1 and
Step 2 MUST preserve those outputs byte-for-byte.

The invariant is:

```text
before Step 1 SQL bytes == after Step 1 SQL bytes
before Step 2 ansi SQL bytes == after Step 2 duckdb SQL bytes
```

for the full required corpus, with Doris and ClickHouse also unchanged through the
shared-baseline extraction.

Any hash change during Step 1 or Step 2 is not "part of the refactor". It is a
potential latent divergence or correctness change and MUST be triaged individually:

- if the previous behavior was correct, restore byte identity;
- if the previous behavior was incorrect, declare the bug explicitly and move the
  fix to Step 3 or a separate correctness PR;
- if a dialect difference is intentional, name and test that difference explicitly.

This turns common-baseline extraction into an audit of the three existing forks
rather than an unobservable rewriting of them.

### Rename the real-engine target to DuckDB

The current split:

```text
tests/engine/ansi/
Backend{Name: "ansi"}
DuckDB CLI executes the SQL
```

becomes:

```text
tests/engine/duckdb/
Backend{Name: "duckdb"}
DuckDB CLI executes the SQL
```

Environment variables and implementation details may continue to use names such
as `DUCKDB_BIN` because they already identify the actual engine.

Compiler golden SQL, snapshots, required-scenario accounting, target matrices, and
per-dialect unsupported lists must use `duckdb` rather than `ansi` when the output
is intended for DuckDB.

A test of a truly target-independent SQL AST transformation may remain dialect
neutral. A test that renders physical SQL must be attributed to a concrete
renderer.

## Capability and API consequences

Native-engine capability discovery currently derives dialects from the registry.
Once the registry changes, callers should observe:

```json
{
  "dialects": ["clickhouse", "doris", "duckdb"]
}
```

A compile request with:

```json
{"engine":"metis-native","dialect":"duckdb"}
```

is supported.

A compile request with:

```json
{"engine":"metis-native","dialect":"ansi"}
```

is unsupported and fails closed through `UNSUPPORTED_DIALECT` / `CHANGE_TARGET`.
No hidden fallback to DuckDB is permitted.

The returned `compiler.SQLQuery.Dialect` must equal the concrete selected dialect.

## Migration plan

Implementation MUST land in reviewable stages. The first two stages are explicitly
**zero-SQL-change phases**.

### Step 1 — extract the common rendering baseline

Goal: remove correctness debt from the three independent renderer forks without
changing any emitted SQL.

- capture the per-case SHA-256 baseline for all 96 canonical scenarios for the
  current `ansi`, Doris, and ClickHouse renderers;
- identify behavior that is genuinely identical across the three implementations;
- extract that behavior into neutral unexported helpers;
- preserve target-owned implementations wherever behavior is known to diverge;
- introduce fail-closed override points for known divergence rather than defaults;
- keep public target names and capability behavior unchanged during this step.

**Hard gate:** all existing SQL output MUST remain byte-identical for all 96
canonical scenarios across all three renderers. A changed fingerprint blocks the
refactor until it is restored or the change is moved into a separately declared
correctness change.

This step is not "moving the ANSI renderer". It is extracting a common baseline
from three forks that may have drifted and using byte identity as the audit.

### Step 2 — replace the `ansi` identity with `duckdb`

Goal: make DuckDB a first-class concrete dialect without changing the SQL it
currently executes successfully.

The current inventory includes 36 repository files referencing `ansi`; the
implementation must update the complete repository-owned surface rather than only
the registry.

- add or rename the concrete renderer to `DuckDBDialect` with name `duckdb`;
- replace repository-owned `dialect: ansi` values with `dialect: duckdb`;
- update CLI/request fixtures and compiled-output assertions;
- update expression-target resolution tests without changing the upstream
  `ANSI_SQL` fallback contract;
- remove `ANSIDialect` from `DefaultDialectRegistry` and register
  `DuckDBDialect`;
- rename `tests/engine/ansi` to `tests/engine/duckdb`;
- register the real-engine backend as `duckdb`;
- rename CI / Make targets and evidence labels where they identify the concrete
  target;
- update capability, documentation, examples, release notes, and evidence rows;
- remove physical-renderer ANSI terminology that exists only as the old target
  identity.

**Hard gate:** the SQL emitted for each scenario after selecting `duckdb` MUST be
byte-identical to the SQL emitted for the same scenario by `ansi` immediately
before the rename. Doris and ClickHouse output MUST also remain byte-identical.

At the end of Step 2:

```text
public dialects = clickhouse, doris, duckdb
ansi            = unsupported
```

No SQL semantic change is permitted to hide inside the rename.

### Step 3 — explicit DuckDB correctness changes

Only after Step 2 is complete may DuckDB-specific rendering changes intentionally
change SQL text.

Each such change MUST be independently reviewable and must state:

- which SQL bytes change and why;
- whether the previous behavior was incorrect, underspecified, or merely less
  target-specific;
- the DuckDB semantic behavior being targeted;
- compiler/golden evidence;
- real-engine result evidence;
- whether Doris or ClickHouse require a corresponding explicit choice.

Known divergence discovered while extracting the shared baseline belongs here, not
inside Step 1 or Step 2.

Step 1 found two such divergences. Both are recorded as declared per-dialect
answers in `dialectBehavior` rather than resolved, because resolving either
would change behavior inside a phase that must not:

1. **Inequality spelling.** The renderers emit `<>` and `!=` for the same
   operator. ClickHouse accepts both, so this is very likely fork drift rather
   than a requirement. Normalizing it changes emitted SQL and therefore moves
   fingerprints.
2. **Degenerate-expression strictness.** Only one fork rejected a logical
   expression with no terms or a function call with no name; the others render
   the empty string and a bare `()` into otherwise valid SQL. Unifying the three
   on the strict answer changes what two renderers accept.

The second one is worth stating precisely, because it is the case where byte
identity is not evidence: the canonical corpus contains no degenerate
expressions, so the fingerprints are unchanged whichever answer each renderer
gives. A refactor phase whose only gate is byte identity therefore cannot
authorize that change, and a passing gate must not be read as having cleared it.

This sequencing is deliberate:

```text
PR A: shared-baseline extraction
      zero SQL output changes
           |
           v
PR B: ansi -> duckdb identity migration
      zero SQL output changes
           |
           v
PR C+: declared DuckDB correctness changes
       SQL changes allowed and evidenced
```

### Step 4 — lifecycle closure

RFC-0035 may move to Implemented only when:

- `ansi` is absent from the default physical dialect registry;
- `duckdb` is a first-class concrete renderer;
- native-engine capabilities advertise DuckDB rather than ANSI;
- compiler and real-engine conformance both key evidence by DuckDB;
- repository docs and examples no longer advertise `ansi` as a compile target;
- no physical-renderer API or filename retains ANSI terminology merely as a name
  for common/default implementation code;
- known renderer divergences cannot silently inherit a common default;
- required correctness, E2E, and all registered real-engine corpora are green.

## Compatibility

This is intentionally a pre-v0.1 contract correction.

RFC-0035 does not promise a deprecation period for `dialect=ansi`. A deprecation
alias would make the public target surface less honest during the exact release
where Metis is establishing its first compatibility contract.

If external usage is discovered before implementation merges, maintainers should
re-evaluate migration messaging, but the architectural end state remains the
same: concrete targets only.

## Rejected alternatives

### Keep `ansi` and add `duckdb` as a fourth dialect

Rejected. Two public targets would largely share one implementation and one
execution corpus, while only DuckDB has concrete runtime semantics. This preserves
rather than resolves the ambiguity.

### Rename `ansi` to `portable`

Rejected. `portable` would make a similar cross-engine compatibility claim without
cross-engine evidence. Portability may be an implementation goal or future tested
profile, but it should not be a physical dialect identity today.

### Keep `ansi` as an alias for DuckDB

Rejected. An alias hides a target change and lets callers continue to describe a
DuckDB execution contract with the wrong name. Unsupported legacy input should
fail explicitly.

### Model DuckDB only as a test backend

Rejected. If Metis knows the execution target is DuckDB and generates SQL whose
correctness is validated against DuckDB semantics, DuckDB is precisely the
physical dialect identity the compiler should expose.

### Make the common baseline answer every operation

Rejected. This maximizes reuse by silently turning absence of a target override
into behavior. For known engine differences that creates plausible but potentially
wrong SQL. Shared code is allowed only where the behavior is genuinely shared;
known divergence must remain an explicit target-owned choice.

### Combine the rename with DuckDB-specific SQL fixes

Rejected. A combined change cannot demonstrate whether a SQL diff came from
identity migration, baseline extraction, or an intended semantic correction.
The first two migration steps require byte identity; correctness changes follow as
separately declared work.

### Remove all shared/default rendering abstractions

Rejected. The issue is not reuse; it is confusing reuse with target identity or
using reuse where engines actually disagree. Shared helpers remain desirable when
multiple concrete renderers genuinely share behavior.

## Consequences

### Benefits

- capability discovery names executable targets rather than an abstract profile;
- compiled output states where its SQL is intended to run;
- DuckDB-specific behavior has an explicit ownership boundary;
- real-engine evidence directly matches the renderer it validates;
- future targets such as Postgres or Snowflake fit the same model naturally;
- internal code reuse no longer implies ANSI standards compliance;
- duplicated renderer logic becomes auditable correctness infrastructure rather
  than three silent forks;
- byte-identity gates make refactoring and identity migration independently
  reviewable;
- known dialect divergences fail closed instead of inheriting an accidental
  default;
- the physical renderer architecture follows MetricFlow's useful separation
  between default implementation reuse and concrete engine renderers.

### Costs

- the current renderer implementations contain roughly 460 duplicated lines that
  must be audited while extracting a common baseline;
- at review time, 36 repository files reference `ansi` and must be migrated across
  Go, YAML, JSON, shell, and Markdown;
- the extraction and rename require fingerprint baselines and byte-identity checks,
  increasing short-term migration work;
- pre-release callers using `dialect=ansi` must change to a concrete target;
- DuckDB-specific correctness fixes may change compiled SQL **after** the
  byte-identical refactor and rename are complete, and those changes must land as
  separately declared work.

These costs are acceptable before v0.1.0 and would become more expensive after the
first public compatibility contract.

## Non-goals

RFC-0035 does not:

- add PostgreSQL, Snowflake, BigQuery, or other new production dialects;
- make DuckDB a production query-execution service inside Metis;
- change Metis's boundary that it compiles but does not execute analytical
  queries;
- remove Ossie `ANSI_SQL` semantic-expression fallback;
- claim DuckDB SQL is portable to arbitrary SQL engines;
- redesign the SQL AST;
- require class inheritance or a specific internal renderer abstraction;
- authorize SQL output changes during shared-baseline extraction or the
  `ansi`-to-`duckdb` identity migration.

## Acceptance criteria

The implementation is complete when all of the following are true:

1. `DefaultDialectRegistry().Names()` includes `duckdb`, `doris`, and
   `clickhouse`, and does not include `ansi`.
2. `CompileTarget{Engine: "metis-native", Dialect: "duckdb"}` compiles the full
   required corpus and returns `SQLQuery.Dialect == "duckdb"`.
3. `dialect=ansi` fails with the ordinary unsupported-dialect contract and is not
   silently redirected.
4. DuckDB has a concrete renderer type and target-owned tests.
5. Real-engine conformance is registered under DuckDB and executed by DuckDB.
6. Target evidence contains a DuckDB row and no ANSI row.
7. Physical-renderer source names no longer use ANSI as a synonym for common or
   default rendering behavior.
8. Ossie `ANSI_SQL` fallback remains supported according to the semantic-model
   contract and is tested independently of the physical dialect name.
9. Step 1 has captured per-case fingerprints and proves byte-identical SQL for all
   96 canonical scenarios across the existing three renderers before and after
   common-baseline extraction.
10. Step 2 proves every DuckDB scenario emits SQL byte-identical to the immediately
    preceding `ansi` output, with Doris and ClickHouse also unchanged.
11. Every known cross-engine rendering divergence has an explicit target-owned
    implementation or fails closed; it cannot silently inherit a common default.
12. Any intentional DuckDB SQL change occurs only after the byte-identical rename
    and is separately declared with compiler and real-engine evidence.
13. `make check`, `make test-e2e`, and every registered real-engine corpus pass.
